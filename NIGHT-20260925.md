# Night 2026-09-25 — segment: making the L3 tier pay for itself

This note records what changed in the engine-side integration, why, and the
measured numbers. The standalone module in `src/`/`include/` still reflects the
pre-night state; refreshing it plus a regenerated
`patches/ninfer-disk-kv-l3-full.patch` is the next step (the working tree used
tonight has no git metadata, so no honest patch could be produced from it).

## 1. The store's lock, not the NVMe, was the read ceiling

`DiskKVStore::read_page_result` held `mu_` across the 1.18MB CRC32 + `memcpy`,
so every reader serialized at ~1.2 ms/page (~980MB/s).

Change (`disk_kv_store.{h,cpp}`):
- two-phase read: under the lock only index lookup + header validation +
  `readers_[slot]++`; CRC and copy outside it; a second short lock decrements.
- eviction (`evict_one_lru`, explicit `evict`) skips slots with `readers_ != 0`,
  otherwise a copy could read a recycled slot (spurious BadCRC, valid page lost).

Measured: single reader 0.43 ms/page (2.6GB/s), 8–32 in flight 0.07 ms/page
(12–17GB/s page-cache bound). Engine-visible: a 2,922-page / 3.4GB restore of a
93K-token session went from 3.5–10s to **1.0–1.4s**, with the whole request
finishing in **1.5s** against 19–26s of full prefill.

Safety: new `tests/disk_kv_parallel_read_stress.cpp` (6 readers hammering pages
while a writer forces continuous LRU eviction) — 0 mismatches, 0 BadCRC /
BadIdentity under ASan/UBSan; `disk_kv_store_test` and `disk_kv_read_ticket_test`
still pass.

## 2. Restore batching + request-path priority

The seed read one page per scheduler visit (~1461 visits ≈ 52s for a 93K prompt,
slower than recomputing it). Now it submits a whole 32-page scratch per visit and
performs ONE `copy_from_host`, with the request-path reads on the priority queue
(they were on the ordinary queue, behind the on-demand spill flood, so batches
shrank to whatever the queue admitted — `max_batch` stuck low, 26s restores).

A multi-ticket batch cannot be polled through a single-ticket cancellation
contract on its own: the batch writes an AGGREGATE ticket that only turns
terminal when every part does, and `poll_seed_batch()` runs before every poll of
the old single ticket — seed entry, `fail()`, the teardown busy-wait loop and the
cancel path. Missing the teardown loop or the cancel path wedges the context
transaction.

## 3. Worker count

`DiskKVBridge::kWorkerCount` 3 → 8: cold reads scale only with concurrency here
(7–10MB/s single, ~200–230MB/s at eight readers), and the write side (evictions)
benefits too — measured 0.84 ms/page for large owner spills against 12.6 ms/page
before (65s → 2.4–4.4s for a fat session).

## 4. Cold reads are the real limit — so restores get a budget

Dropping the page cache (`sync; echo 3 > /proc/sys/vm/drop_caches`) and reading
the production store file: mmap faults 7/65/184 MB/s, buffered pread 9/80/230,
O_DIRECT no better, at 1/4/8 threads. Earlier `dd` numbers of 421MB/s (and
883MB/s at four streams) were page-cache hits, not transfer rates.

Consequence: a restore is 1.0–1.4s while the session is still cached (13–17x
better than prefill) but 15–30s once it has fallen out of the 27GB cache over the
44GB store. A disk hit must therefore never cost more than recomputing:
- `NINFER_SEED_BUDGET_MS` (default 8000) bounds the restore; on expiry the seed
  takes the existing honest-recompute path (partial state rolled back,
  `advertised_base=0`) and logs
  `reason=budget elapsed_ms=… -> honest full recompute`.
- verified: budget=800 → `reason=budget elapsed_ms=1528 -> honest full recompute`
  with the request completing normally; the fast path keeps landing `state=ok`.

## 5. Measurement hygiene (two wasted rounds)

- Never run a storage benchmark while the engine serves a load test on the same
  store: both sets of numbers collapse (bench 7MB/s, and 5 of 8 load-test fills
  timed out with `inference request expired while waiting for admission`).
- A candidate container named `ninfer` on port 9999 receives the user's real
  agent traffic; synthetic load then competes with it and both slow down.
- Verify the launched container's IMAGE (`docker inspect … {{.Config.Image}}`),
  not just `/health`: after `rm -f` the name can still be held, the `docker run`
  fails, and the stale container answers health and a real probe request.
